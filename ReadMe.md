## 3. Задание

Инициализация проекта через `npm init`, настройка `package.json`. Создание серверного приложения на Node.js и Express. Специфические требования по варианту:

* **Структура API:** Реализовать полноценное REST API для управления ресурсом `backupTypes` со следующими операциями:
    * `GET /backupTypes` — получение списка всех карточек (с возможностью фильтрации по названию через query-параметр `title`).
    * `GET /backupTypes/:id` — получение карточки по её идентификатору.
    * `POST /backupTypes` — создание новой карточки.
    * `PATCH /backupTypes/:id` — частичное обновление существующей карточки.
    * `DELETE /backupTypes/:id` — удаление карточки.
* **Хранение данных:** Данные должны храниться в JSON-файле (`data/backupTypes.json`) и управляться через файловую систему с помощью синхронных методов (`fs.readFileSync`, `fs.writeFileSync`).
* **Архитектура:** Код должен быть разделен на слои для обеспечения модульности и переиспользуемости:
    * **Слой маршрутов (Routes):** Определяет конечные точки API.
    * **Слой контроллеров (Controllers):** Обрабатывает входящие запросы, вызывает сервисы и формирует ответы.
    * **Слой сервисов (Services):** Содержит бизнес-логику (поиск, фильтрация, валидация).
    * **Слой работы с файлами (File Service):** Абстрагирует работу с файловой системой.
* **Требования к безопасности:** Настроить CORS для доступа с локальных хостов, использовать helmet для защиты HTTP-заголовков и ограничить количество запросов с одного IP (rate limiting).

## 4. Теория и реализация (Примеры из кода)

### 4.1. Слоистая архитектура и инкапсуляция FS

**Теория:** Слоистая архитектура — это шаблон проектирования, который разделяет приложение на логические слои, каждый из которых имеет свою ответственность. Такой подход упрощает тестирование, поддержку и масштабирование проекта.

В данной работе слой маршрутов (`backupTypes.js`) определяет доступные эндпоинты. Контроллер (`backupTypesController.js`) обрабатывает запросы и формирует ответы. Сервис (`backupTypesService.js`) содержит бизнес-логику. Слой работы с файлами (`fileService.js`) полностью изолирует логику чтения и записи данных, что позволяет легко сменить способ хранения (например, на базу данных) без изменения остального кода.

**Пример из кода (Сервис для работы с файлами):**
``` js
    // services/fileService.js
    const fs = require('fs');

    const readData = (filePath) => {
        try {
            const data = fs.readFileSync(filePath, 'utf8');
            return JSON.parse(data);
        } catch (err) {
            console.error('Ошибка чтения файла:', err);
            return [];
        }
    };

    const writeData = (filePath, data) => {
        try {
            fs.writeFileSync(filePath, JSON.stringify(data, null, 2), 'utf8');
        } catch (err) {
            console.error('Ошибка записи файла:', err);
        }
    };

    module.exports = { readData, writeData };
```
Этот код демонстрирует простой и эффективный способ абстрагирования файловых операций. Функция `readData` загружает и парсит JSON, а `writeData` — сохраняет данные обратно в файл.

### 4.2. Маршрутизация, контроллеры и обработка JSON

**Теория:** Фреймворк Express предоставляет мощные инструменты для создания маршрутов (routes) и обработки запросов. Встроенный middleware `express.json()` автоматически парсит входящие JSON-запросы и делает данные доступными через `req.body`. Контроллеры служат связующим звеном между маршрутами и сервисами: они извлекают данные из запроса (параметры URL, query-строку, тело запроса), вызывают соответствующие методы сервиса и отправляют ответ клиенту с правильным HTTP-статусом.

**Пример из кода (Маршруты и контроллер):**
``` js
    // routes/backupTypes.js
    const express = require('express');
    const router = express.Router();
    const backupTypesController = require('../controllers/backupTypesController');

    router.get('/', backupTypesController.getAllBackupType);
    router.get('/:id', backupTypesController.getBackupTypeById);
    router.post('/', backupTypesController.createBackupType);
    router.patch('/:id', backupTypesController.updateBackupType);
    router.delete('/:id', backupTypesController.deleteBackupType);

    module.exports = router;

    // controllers/backupTypesController.js (фрагмент)
    const createBackupType = (req, res) => {
        const { src, title, text } = req.body;
        if (!src || !title || !text) {
            return res.status(400).json({ error: 'Не все поля заполнены' });
        }
        const newBackupType = backupTypesService.create({ src, title, text });
        res.status(201).json(newBackupType);
    };
```
Как видно из кода, каждый маршрут делегирует обработку соответствующему методу контроллера. Контроллер, в свою очередь, выполняет валидацию входных данных и, в случае успеха, возвращает статус `201 Created` вместе с созданным объектом.

### 4.3. Обновление данных через Spread-оператор

**Теория:** При частичном обновлении ресурса (PATCH-запрос) клиент может отправить только те поля, которые необходимо изменить. Для корректного слияния существующих данных с новыми в JavaScript удобно использовать spread-оператор (`...`). Этот оператор создает новый объект, копируя в него все свойства исходного объекта, а затем перезаписывает указанные поля новыми значениями.

**Пример из кода (Обновление в сервисе):**
``` js
    // services/backupTypesService.js (фрагмент)
    const update = (id, backupTypeData) => {
        const backupTypes = fileService.readData(dataFilePath);
        const index = backupTypes.findIndex(s => s.id === id);
        if (index === -1) return null;
        backupTypes[index] = { ...backupTypes[index], ...backupTypeData };
        fileService.writeData(dataFilePath, backupTypes);
        return backupTypes[index];
    };
```
В этом фрагменте `{ ...backupTypes[index], ...backupTypeData }` создает новый объект, в котором все свойства существующей карточки объединяются со свойствами из `backupTypeData`. Приоритет имеют свойства из `backupTypeData`. Таким образом, если клиент отправил только поле `title`, остальные поля (`src`, `text`) останутся неизменными.

### 4.4. Безопасность и ограничение частоты запросов

**Теория:** При разработке серверных приложений важно обеспечить их базовую защиту. Helmet помогает обезопасить приложение, устанавливая различные HTTP-заголовки. CORS (Cross-Origin Resource Sharing) контролирует, какие домены могут обращаться к API. Rate limiting ограничивает количество запросов от одного IP-адреса за определенный промежуток времени, предотвращая DoS-атаки и чрезмерную нагрузку.

**Пример из кода (Настройка безопасности и лимитов в `index.js`):**
``` js
    // src/index.js (фрагмент)
    const express = require('express');
    const CORS = require('cors');
    const helmet = require('helmet');
    const rateLimit = require('express-rate-limit');
    
    const app = express();
    
    app.use(helmet());
    
    const corsSettings = {
        origin: (origin, callback) => {
            if (!origin || origin.startsWith('http://localhost') || origin.startsWith('https://localhost')) {
                callback(null, true);
            } else {
                callback(null, false);
            }
        }
    };
    app.use(CORS(corsSettings));
    
    const limiter = rateLimit({
        windowMs: 60 * 1000, // 1 минута
        limit: 30,           // максимум 30 запросов
        message: 'Too many requests from this IP, please try again later.'
    });
    app.use(limiter);
```
В данном примере CORS настроен таким образом, чтобы разрешать доступ только с локальных хостов (`localhost` и `127.0.0.1`). Лимитер ограничивает 30 запросов в минуту, что является разумным лимитом для учебного проекта и защищает сервер от перегрузки.
